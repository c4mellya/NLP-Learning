前缀复用与缓存成本

大模型 API 的 Prompt Caching（提示词缓存）依赖一个核心条件：请求具有完全一致的前缀。前缀保持稳定，才有机会复用已有计算、降低输入成本；前缀发生变化，变化位置及其后续内容就需要重新处理。这份笔记从机制、交互示例和成本模拟三个角度展开，你可以边读边调整参数，观察结论如何变化。

sec.1 / 5 · 机制

缓存机制：复用前缀的 KV 状态

在采用因果注意力的 Transformer 中，生成第 t 个 token 时会用到前 t-1 个 token 的键（Key）和值（Value）。在模型与计算配置一致的条件下，这些 K/V 状态由对应前缀决定，不依赖后续追加的问题。因此，服务商可以暂存前缀的计算状态，在后续请求满足匹配条件时直接复用，减少重复计算。

如果你用过本地推理中的 KV cache，可以把 prompt caching 理解为将复用范围从「一次请求内部」扩展到「多次请求之间」。它主要减少预填充（prefill）阶段的重复计算，进而降低输入成本和首 token 延迟。

[a]从前缀开始匹配

匹配从输入开头开始。尾部追加内容可以保留已有前缀；前缀内部发生变化时，变化位置及其后续状态无法直接复用。

[b]要求精确一致

前缀缓存依赖精确匹配，而非语义相似。换一个字或多一个空格，都可能改变实际输入；含义相近并不等于缓存可复用。

[c]受有效期约束

缓存具有有效期（TTL）：Anthropic 5 分钟档命中即刷新（另有 1 小时档）；OpenAI GPT-5.6+ 的 ttl 默认 30m；DeepSeek 可达数小时至数天。过期后需要重新建立缓存。

成本模拟：缓存能节省多少

本节采用简化模型：每轮请求由稳定前缀与逐轮追加的内容组成。无缓存时，全部输入按标准价格计费；命中时，复用部分按读取价格、新内容按标准价格计费；失效轮次则按写入价格重新计算。前缀低于设定的最小可缓存长度时，模型按无缓存处理，并显示提示。结果以「等效全价输入 token」表示，可结合每百万 token 的单价换算为美元。

sec.5 / 5 · 常见问题与使用判断

常见失效原因与使用建议

实际使用时，动态内容的位置、序列化方式和前缀长度都会影响缓存效果。可以先检查下面五种情况，再判断缓存是否适合当前请求模式。

问题 1 · 在前缀开头插入时间戳

把当前时间拼在 system 最前面，等于每轮换一个前缀。

system = "现在 " + now + "\n" + BASE // 每轮都不同 → 永远冷启动
BASE 保持字节稳定；now 放进最后一条 user 消息

问题 2 · 增删或重排 tools

工具定义位于前缀。新增工具或调整顺序，会影响变化位置及其后续前缀的复用。

tools 数组每次重新排序 / 条件拼接 // 前缀字节变化
工具集固定序列化；必须变时，接受一次写价重写

问题 3 · JSON 键顺序不固定

将 JSON 文本放入 prompt 时，即使内容相同，键顺序不同也会改变输入序列。

{"b":1,"a":2} 与 {"a":2,"b":1} // 逐字节比较 → 不相等
固定键序（如 sort_keys）后再进 prompt

问题 4 · 动态内容位于断点之前

RAG 检索结果每次不同，却拼进 system 或断点之前。

system = 检索结果 + 规则 // 检索一变，全失效
规则与静态文档走缓存；检索结果放到尾部再追加

问题 5 · 未达到最小可缓存长度

前缀没到最小可缓存长度，或断点打在了太靠前的位置：接口不报错，只是永远不命中。

prefix = 400 token // 低于该模型的最小可缓存长度 → 无法建立缓存，因此不会命中
先确认长度门槛，再评估写入成本与复用收益

判断顺序 · 先门槛，再前缀，最后 TTL

按以下顺序检查，有助于在发起请求前判断缓存是否具备复用条件。

1) 前缀够长吗？（Anthropic 512–4,096 / DeepSeek 无明示） 2) 前缀字节真的稳定吗？（ tools / 键序 / 时间戳） 3) 会在缓存有效期内复用吗？（间隔短于 TTL）

[+]适合使用缓存的情况

  • 前缀达到门槛（Anthropic 依模型 512–4,096 token）且重复使用 ≥2 次
  • 固定文档库 / RAG 语料放在最前，逐题只改尾部
  • Agent 的 system + tools 固定，多轮对话用追加式
  • 请求间隔短于 TTL，或通过持续命中刷新有效期
  • 写溢价的一次性成本能被多次读摊薄（Anthropic 5 分钟档 1 次读即回本）

[-]收益有限或成本增加的情况

  • 只问一次：Anthropic 写价 1.25×（GPT-5.6+ 同样收 1.25×），没有后续读取来抵消写入溢价
  • 前缀短于门槛：无法建立缓存，仍按标准输入价格计费
  • 每轮都改动前缀：失效一次，整个前缀按写价重算
  • 超过 TTL 再来：冷启动 + 重新写一遍

# Prompt 迭代日志

子任务：C — Prompt Caching / Prefix：为什么前缀稳定能省钱。
参考：[OpenAI 文档](https://developers.openai.com/api/docs/guides/prompt-caching)、[Anthropic 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

## 第 1 版 Prompt

```text
# Task
制作一个单页知识网页，向学过 Transformer 和 Python 的学生解释 Prompt Caching，以及为什么稳定前缀能省钱。

# Constraints
使用原生 HTML、CSS、JavaScript，包含动画或交互。引用 OpenAI 和 Anthropic 官方文档，避免无关内容。页面采用暖纸色、橙红强调，文字清晰，桌面与手机都能阅读。

# Data
核心概念：相同前缀复用已计算的 KV，前面的内容变化会影响后面的计算。
对比场景：只改问题、在 system 开头插入时间戳、调整工具列表顺序。
参考资料：两家官方 Prompt Caching 文档。

# Output
index.html 及所需 CSS、JS，包含概念说明、缓存交互和 API 示例。
```

### 输出问题

首稿把“有交互”主要理解为切换几组预设动画，学生能看到颜色变化，却不能编辑自己的请求，也难以判断变化究竟发生在哪里。说明文字把“前缀相同”和“缓存一定命中”混在一起，没有分开解释长度门槛与过期条件。

另一个问题是缓存状态不明确：如果编辑文本时立即写入缓存，就会把“准备请求”和“发送请求”混成同一步，学生无法比较当前输入和上一次已发送的输入。API 对比也偏向列代码，没有解释三个 Anthropic 用量字段的关系。

### 问题归因

“做一个可交互网页”只描述了外观，没有规定输入、状态转换、反馈和判断依据。Agent 可以完成形式上的交互，却不一定完成教学目标。需要把可观察的行为写进规格。

## 第 2 版 Prompt

```text
# Task
在现有页面上完善前缀缓存实验。让学生先编辑一条请求，再与缓存中的历史请求比较，清楚看到第一处分叉及其后重算。核心概念保持为“稳定前缀为何能复用计算”。

# Constraints
不要重做整页，不新增其他知识点。保留现有视觉与原生实现。
把请求按工具定义、系统规则、参考资料、用户问题四段排列，每段可编辑。
编辑只更新当前请求的预览；点击“发送这次请求”才记录缓存。
提供三个操作：在规则开头插入时间戳、调换工具顺序、只换用户问题。
标出分叉点，分开显示读取缓存、写入缓存和重新计算；过期操作清空缓存。
OpenAI 演示自动前缀匹配，Anthropic 演示显式 cache_control 断点。
展示各自的 usage 字段，并解释缓存读取、缓存写入与普通输入如何计入成本。
所有 token 和成本都标为教学模拟，不当作真实 API 结果。
遵循减少动效偏好，切换和反馈保持键盘可操作。

# Data
第一版问题：只有预设动画；缺少可编辑输入、明确发送时机、长度与过期边界，以及用量字段解释。
稳定内容放前面，每轮变化的问题放最后；变化发生在中间时，不能跳过分叉点复用后半段。
官方资料：OpenAI 与 Anthropic 的 Prompt Caching 文档。

# Output
完善请求编辑区、缓存网格、用量和成本显示，并保留 API 对比与多轮 Agent 示意。说明本轮修改的规格与对应效果。
```

### 改了哪部分规格

第二版把笼统的“可交互”改成明确的输入和动作：四段编辑器、发送按钮、过期按钮和三种改动场景；把缓存读写与当前请求分开；把“看到动画”改成“识别分叉位置并解释后续为什么重算”。

同时补上数据身份和成本口径：简化 token 用于教学，价格采用具体示例倍率；不同服务商的用量字段分别展示，不用一个“命中率”替代全部语义。

### 效果变化

第二版方案可以沿着一条明确的学习路径展开：只换末尾问题时，前面的稳定部分继续复用；在规则开头插入时间戳时，分叉提前，后面的内容需要重新计算；调整工具顺序时，影响发生在更前面。学生可以直接改字，观察影响，而不只是播放预设动画。

“发送”与“编辑”分开后，上一次请求成为明确的参照。过期按钮说明前缀一致仍不等于永远命中。两家 API 的字段与成本放在同一区域后，也能解释为什么 Anthropic 首次写入可能更贵，而后续读取更便宜。

## 结论

这个知识点最应在哪一层解决：☑ Runtime；Prompt 与 Eval 配合，Schema 负责必要的结构约束。

缓存复用依赖请求在运行时如何排列、哪些内容变化及何时发送。Prompt 可以要求稳定顺序，但最终要由程序保证；Schema 能限制结构，不能自动保证前缀稳定。Eval 应围绕“只改问题、开头改字、缓存过期”定义可观察的判断标准。

我学到的方法：先规定输入、状态变化和可观察结果，再让 Agent 实现界面；出现问题时修改具体规格，而不是只补一句“再优化一下”。

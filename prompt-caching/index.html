Prompt Caching为什么前缀稳定能省钱

模型按顺序读 prompt。开头和上一次一模一样，算过的部分就能直接复用；改动一个字，从那里往后全部重新计算。

          Kj, Vj = f(x1, …, xj)
          xi 变了 ⇒ 所有 j ≥ i 都要重算
        

        

          
为什么必须从头一致

          
解码器用的是因果注意力：第 j 个 token 的 Key 和 Value 只由它自己和前面的 token 决定。服务端把一段前缀算好的结果保存下来，下次遇到同样的开头，就跳过这段计算，从分叉处接着算。

          
反过来，第 i 个 token 一变，后面每个 token 都在注意力里“看过”它，它们的结果全部过期。所以缓存只能匹配前缀，不能跳过中间的改动去复用后半段。

项目OpenAIAnthropic

          
            
开启方式支持的模型自动开启，不用改代码在 tools、system 或 messages 的内容块上加 cache_control，最多 4 个断点

            
前缀顺序按请求内容的先后，tools 也算在内固定为 tools → system → messages；改 tools 会让后面全部失效

            
最短长度1024 tokens随模型不同，见官方表格

            
如何匹配最长的相同前缀，以 128 tokens 为步长在断点处查找；没命中时向前回溯约 20 个内容块

            
有效期闲置 5–10 分钟后清除，最长约 1 小时；部分模型可设 prompt_cache_retention 延长默认 5 分钟，每次命中重新计时；可设 "ttl": "1h"

            
价格命中部分按折扣价，没有写入费写入 1.25×（1 小时缓存为 2×），读取 0.1×

Python

          
from openai import OpenAI

client = OpenAI()
RULES = open("course_notes.md", encoding="utf-8").read()  # 需超过 1024 tokens

for question in ["什么是前缀缓存？", "为什么时间戳要放在最后？"]:
    resp = client.chat.completions.create(
        model="gpt-4.1",
        messages=[
            {"role": "system", "content": RULES},
            {"role": "user", "content": question},
        ],
    )
    usage = resp.usage
    print(usage.prompt_tokens, usage.prompt_tokens_details.cached_tokens)

          
第一次 cached_tokens 为 0；第二次接近 RULES 的长度。缓存按最佳努力路由，没有命中时隔几秒再发一次。

        

                

          
Python

          
import anthropic

client = anthropic.Anthropic()
RULES = open("course_notes.md", encoding="utf-8").read()  # 需超过模型的最短可缓存长度

for question in ["什么是前缀缓存？", "为什么时间戳要放在最后？"]:
    resp = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=512,
        system=[{"type": "text", "text": RULES,
                 "cache_control": {"type": "ephemeral"}}],
        messages=[{"role": "user", "content": question}],
    )
    u = resp.usage
    print(u.cache_creation_input_tokens, u.cache_read_input_tokens, u.input_tokens)

          
第一次 cache_creation_input_tokens 大于 0；第二次变为 0，cache_read_input_tokens 等于 RULES 的长度。

        

                

      

      
验收第二次请求读到缓存；开头改一个字符后命中归零；能说清两家用量字段各自统计什么。在 Hermes 中，可以用 /usage 观察多轮对话的 token 消耗。
